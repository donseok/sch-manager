## 1. 기술 요약

본 시스템은 **Next.js 14 App Router**를 기반으로 하는 풀스택 웹 애플리케이션으로, 프론트엔드와 백엔드(API Routes)가 단일 프로젝트 내에서 통합 운영됩니다. **Prisma ORM**을 통해 **PostgreSQL**(Neon/Vercel Postgres)에 접근하며, 클라이언트 상태 관리는 **Zustand**, UI 스타일링은 **Tailwind CSS**를 사용합니다.

별도의 백엔드 서버(Spring Boot 등) 없이 Next.js API Routes가 비즈니스 로직을 처리하는 서버리스 아키텍처를 채택하여, 개발·배포·운영의 복잡도를 최소화했습니다. Vercel 플랫폼에 배포되어 자동 스케일링과 글로벌 CDN을 활용합니다.

## 3. 시스템 아키텍처

### 3.1 아키텍처 개요

Next.js 풀스택 아키텍처로 설계된 병동 간호사 근무표 관리 시스템입니다. 프론트엔드(React)와 백엔드(API Routes)가 단일 Next.js 프로젝트 내에서 운영되며, Prisma ORM을 통해 PostgreSQL에 접근합니다. 서버 컴포넌트(대시보드)와 클라이언트 컴포넌트(근무표 편집기)를 최적 분리하여 성능과 인터랙티비티를 동시에 확보합니다.

**아키텍처 스타일**: Full-Stack Monolith (Next.js App Router) + Serverless Deployment

#### Data Layer (Prisma + PostgreSQL)

10개 모델 (prisma/schema.prisma):
- **Ward** — 병동 정보
- **Nurse** — 간호사 사원 정보
- **User** — 시스템 사용자 계정
- **ShiftType** — 근무 유형 마스터
- **Schedule** — 월간 근무표 헤더
- **ScheduleEntry** — 간호사별/일별 근무 배정

- **ScheduleChangeLog** — 수정 감사 이력
- **SchedulePrintLog** — 출력 이력

### 3.4 데이터 흐름

1. **근무표 조회**: 클라이언트 → GET `/api/schedules/[id]/entries` → Prisma 쿼리 → ScheduleEntry + Nurse JOIN → JSON 응답 → Zustand `setGridData()` → ScheduleGrid 렌더링

2. **셀 편집**: ShiftCell 클릭 → 근무코드 선택 → Zustand `updateCell()` → gridData 업데이트 + summary 재계산 → isDirty = true → UI 리렌더

3. **저장**: [저장] 클릭 → PUT `/api/schedules/[id]/entries` { entries, nurseIds } → DB 기존 엔트리 비교 → ChangeLog 생성 → Upsert entries → Summary 재계산 → isDirty = false

4. **확정**: [확정] 클릭 → PATCH `/api/schedules/[id]` { status: "CONFIRMED" } → 기존 확정 근무표 검사 → 빈 셀 검사 → 상태 변경 → 대시보드 반영

5. **대시보드**: Server Component → Prisma 직접 쿼리 (CONFIRMED 스케줄) → 금일 근무현황, 주간 미리보기, 공정성 지표, 알림 계산 → SSR HTML

6. **엑셀 다운로드**: GET `/api/schedules/[id]/excel` → SheetJS로 워크시트 생성 → .xlsx 바이너리 응답 → 브라우저 다운로드

7. **인쇄**: react-to-print → PrintLayout 컴포넌트 렌더링 → 브라우저 인쇄 다이얼로그

## 4. 데이터베이스 설계

### 4.1 데이터베이스 환경

- **엔진**: PostgreSQL (Neon Serverless)
- **ORM**: Prisma 5.22.x
- **연결**: Connection Pooling (`DATABASE_URL`) + Direct (`DATABASE_URL_UNPOOLED`)
- **스키마 관리**: `prisma db push` 또는 `prisma migrate dev`

### 4.2 핵심 제약조건

| 제약 | 설명 |
|------|------|
| `schedules` UNIQUE | (ward_id, year, month, version) — 병동별 월간 근무표 고유 |
| `schedule_entries` UNIQUE | (schedule_id, nurse_id, work_date) — 간호사/일별 중복 방지 |
| `schedule_summaries` UNIQUE | (schedule_id, nurse_id) — 간호사별 집계 고유 |
| CASCADE DELETE | Schedule 삭제 시 entries, summaries, approvals, change_logs, print_logs 연쇄 삭제 |
| 확정 제약 | 같은 ward_id + year + month에 CONFIRMED 상태는 1개만 허용 (API 레벨 검증) |

### 4.3 엔티티 상세

(Prisma 스키마 참조: `prisma/schema.prisma`)

**주요 필드 매핑**:
- 모든 모델: `id` (UUID), `created_at`, `updated_at`
- Nurse: `employee_number` (고유), `position` (HN/CN/AN/RN), `position_rank`, `sort_order`, `employment_status` (ACTIVE/LEAVE/RESIGNED)
- Schedule: `status` (DRAFT/PENDING_MANAGER/PENDING_DIRECTOR/APPROVED/CONFIRMED/REVISED), `version`
- ScheduleEntry: `shift_type_code` (D/E/N/O/X/T/B), `is_modified`
- ScheduleChangeLog: `previous_shift_code`, `new_shift_code`, `version_before`, `version_after`

## 8. 기술 결정 기록 (ADR)

### ADR-001: Next.js 풀스택 (vs Spring Boot 분리)
- **결정**: Next.js API Routes로 백엔드 통합
- **이유**: 소규모 병동 단위 시스템, 별도 백엔드 서버 운영 부담 불필요, Vercel 서버리스로 zero-ops

### ADR-002: PostgreSQL (vs SQLite)
- **결정**: Vercel Postgres (Neon) 사용
- **이유**: Vercel 배포 환경에서 SQLite 사용 불가, Neon 서버리스 PostgreSQL로 connection pooling 지원

### ADR-003: Zustand (vs Redux, Context API)
- **결정**: Zustand으로 근무표 그리드 상태 관리
- **이유**: 근무표 그리드의 고빈도 셀 업데이트에 최소 보일러플레이트, selector 기반 리렌더 최적화

### ADR-004: Custom Grid (vs TanStack Table)
- **결정**: ScheduleGrid 커스텀 테이블 구현
- **이유**: 근무표 특화 요구사항 (드래그 선택, 근무코드 팝업, 요약 행, sticky 헤더/컬럼)이 범용 테이블 라이브러리보다 커스텀 구현이 적합

### ADR-005: SheetJS (vs Apache POI)
- **결정**: SheetJS로 클라이언트/서버 엑셀 생성
